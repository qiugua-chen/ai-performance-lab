## 2. M0 目标

M0 建立不依赖 AI 的性能测试执行闭环，明确指标计算与规则评估口径：

```text
测试规格（Test Spec）
→ JMeter
→ 运行标识（Run ID）
→ JTL
→ 性能指标
→ 规则引擎
→ PASS / FAIL / INVALID
```

M0 在引入 AI 测试规划或 AI 结果分析之前，先验证底层性能工程流程。

## 3. 验收清单

- [x] 输入校验：接受有效 Test Spec，拒绝无效配置。
- [x] 被测服务：通过接口测试验证正常、慢响应和错误响应场景。
- [x] 负载模板：参数化 JMeter 模板可通过命令行独立执行。

- [x] 交付文档：记录环境、指标口径、验收条件与功能边界。

## 7. 自动化测试验收

通过一条命令执行完整自动化测试套件：

```powershell
python -m pytest
```

验收要求：

- 所有测试均被收集；
- 所有测试均通过；
- pytest 进程以退出码 `0` 结束；
- 单元测试无需启动示例 API 服务；
- 单元测试不启动真实的 JMeter 进程；
- 单元测试无需访问网络；
- 临时测试产物不会污染项目工作区。

真实的 JMeter 执行通过端到端场景单独验证。

## 8. 测试规格约定

M0 测试规格定义如下：

```yaml
version: "1.0"
name: "example-test"

request:
  method: "GET"
  url: "http://127.0.0.1:8001/api/normal"

load:
  threads: 1
  ramp_up_seconds: 1
  duration_seconds: 3

acceptance:
  min_rps: 0.1
  min_samples: 3
  p95_ms: 2000
  success_rate: 1.0
```

输入约定包含：

- 请求方法和 URL；
- 线程数；
- 线程启动时间（Ramp-up）；
- 执行时长；
- 最低每秒请求数（RPS）；
- 最小样本数；
- 最大 P95 响应时间；
- 最低成功率。

结构无效的配置会在执行 JMeter 之前被拒绝。

## 9. 运行标识约定

每次执行都会获得唯一的运行标识（Run ID）。

示例：

```text
RUN-20260907T120001123456Z-a1b2c3d4
```

运行标识具有以下组成和特征：

- 可排序的 UTC 时间戳；
- 微秒级精度；
- 低碰撞概率的后缀。

每次运行都会创建独立目录，绝不复用已有运行目录。

同一次执行的全部证据均关联到同一个运行标识。

## 10. 产物约定

每次完成的运行均保留以下文件：

```text
runs/
└── RUN-.../
    ├── test-spec.yaml
    ├── test-plan.jmx
    ├── jtl-save.properties
    ├── result.jtl
    ├── jmeter.log
    ├── metrics.json
    ├── evaluation.json
    └── run.json
```

各产物的用途如下：

| 产物 | 用途 |
|---|---|
| `test-spec.yaml` | 经过校验的原始测试输入 |
| `test-plan.jmx` | 本次执行使用的 JMeter 模板副本 |
| `jtl-save.properties` | 本次执行使用的 JTL 输出配置副本 |
| `result.jtl` | JMeter 原始采样结果 |
| `jmeter.log` | JMeter 执行日志 |
| `metrics.json` | 通过确定性计算得到的性能指标 |
| `evaluation.json` | 规则检查记录和最终状态 |
| `run.json` | 运行标识与执行摘要 |

项目的目录创建和文件写入逻辑拒绝覆盖已有目标；这不等同于文件系统只读或防篡改保护。

本地运行产物不纳入 Git 版本控制。

## 11. JTL 解析约定

M0 解析器支持 CSV 格式的 JTL 文件。

以下字段为必填项：

```text
timeStamp
elapsed
label
responseCode
success
```

解析器行为：

- 将结构有效的 JTL 解析为具有明确类型的样本；
- 明确拒绝空白 JTL 文件；
- 明确拒绝损坏的 JTL 文件；
- 仅含表头的 JTL 在结构上有效，但样本数为零；
- 明确拒绝缺少必填列的文件；
- 明确拒绝无效的数值和布尔值。

## 12. 指标计算约定

确定性指标引擎计算以下指标：

- 请求数；
- 成功数；
- 错误数；
- 观测时长；
- 每秒请求数（RPS）；
- 成功率；
- 错误率；
- 最小响应时间；
- 平均响应时间；
- 最大响应时间；
- P50；
- P90；
- P95；
- P99。

计算遵循以下规则：

- 请求数包含成功和失败的样本；
- 成功率和错误率的取值范围为 `0.0` 至 `1.0`；
- RPS 基于观测到的样本执行时间窗口计算；
- 响应时间统计包含成功和失败的样本；
- 百分位数采用最近秩法（nearest-rank）；
- 小数指标使用 Python `round(value, 6)` 保留至小数点后六位；
- 空样本集不生成指标；
- 拒绝时长为零的执行时间窗口。

仓库中已提交固定的 JTL 数据集，作为指标计算的回归测试数据（golden fixture）。

其预期结果通过人工计算得出：

| 指标 | 预期值 |
|---|---:|
| 请求数 | 10 |
| 成功数 | 8 |
| 错误数 | 2 |
| 时长 | 10.0 秒 |
| RPS | 1.0 |
| 成功率 | 0.8 |
| 错误率 | 0.2 |
| 最小响应时间 | 100 ms |
| 平均响应时间 | 550 ms |
| 最大响应时间 | 1000 ms |
| P50 | 500 ms |
| P90 | 900 ms |
| P95 | 1000 ms |
| P99 | 1000 ms |

指标引擎的结果与上述人工计算值一致。

## 13. 规则评估约定

规则引擎只会输出以下三种状态之一：

```text
PASS
FAIL
INVALID
```

各状态含义如下：

| 状态 | 含义 |
|---|---|
| PASS | 证据有效，且所有指标均满足配置的阈值要求 |
| FAIL | 证据有效，但至少一项指标未满足配置的阈值要求 |
| INVALID | 证据不足或存在内部不一致 |

评估遵循以下规则：

- 先检查证据有效性，再检查性能阈值；
- 样本不足时输出 `INVALID`，而不是 `FAIL`；
- 样本计数或比率不一致时输出 `INVALID`；
- 证据有效但未满足阈值要求时输出 `FAIL`；
- 证据有效且满足全部阈值要求时输出 `PASS`；
- 阈值判断包含边界值；
- 每项未通过的检查都以结构化证据的形式保留。

| 结果 | 退出码 |
|---|---:|
| PASS | 0 |

## 15. 完整工作流命令

Windows 环境示例：

```powershell
python -m ai_performance_lab run --spec "examples\test_specs\normal-e2e.yaml" --jmeter "D:\tools\apache-jmeter-5.6.3\bin\jmeter.bat" --runs-root "runs" --timeout-seconds 30
```

该命令自动完成以下步骤：

1. 创建运行标识；
2. 创建独立的产物目录；
3. 保存执行输入快照；
4. 加载并校验测试规格快照；
5. 调用 JMeter；
6. 生成 JTL；
7. 解析 JTL；
8. 计算性能指标；
9. 评估验收规则；
10. 保存完整结果。

## 17. 最终结论

M0 建立了从测试规格到规则评估结果的执行流程，不依赖 AI。

本项目能够：

1. 加载并校验结构化测试规格；
2. 创建唯一的运行标识；
3. 原样保存执行输入；
4. 通过 Python 调用 Apache JMeter；
5. 生成并校验原始 JTL 证据；
6. 以确定性方式计算性能指标；
7. 评估配置的验收规则；
8. 输出可解释的 PASS、FAIL 或 INVALID 结果；
9. 保存完整运行证据，且不覆盖历史产物。

M0 证明了核心性能工程闭环能够正常工作。

该验收结论仅适用于本文记录的环境与场景，不代表已完成生产可用性验证。AI 测试规划和 AI 结果分析尚未实现。
