# M0 工程复盘

## 1. 阶段目标与结论

M0 完成了从结构化测试规格到性能评估结果的执行闭环，为后续 AI 测试规划提供可独立运行的执行基础。

本阶段的重点是明确输入约束、统一指标口径并保留评估依据。测试编排、指标计算和规则评估均由代码实现，不依赖大语言模型。

这里的“确定性”指相同有效样本和配置得到相同的指标与评估结果；实际压测数据仍会受到被测服务、负载和运行环境的影响。

## 3. 关键设计决策

### 3.1 以结构化输入约束执行范围

M0 采用固定的 HTTP GET 模板，通过 Test Spec 映射 JMeter 参数，明确线程数、Ramp-up 时间、执行时长和验收阈值。

这一方案便于审查执行参数及复现配置，也限制了场景表达能力。更多 HTTP 方法、请求头、请求体和复杂业务链路属于后续扩展范围。

### 3.2 将指标计算与 AI 分析分离

请求计数、RPS、成功率和响应时间百分位数均由代码计算。固定数据集及人工核对的预期值用于验证计算口径，避免仅依靠端到端结果判断公式是否正确。

RPS 使用最早样本开始到最晚样本结束的观测时间窗口，响应时间统计包含成功与失败样本。后续调整统计口径时，需要同步更新测试和文档，以保持结果可比。

### 3.3 区分性能不达标、证据无效与执行错误

| 结果 | 判定依据 | 含义 |
|---|---|---|
| `PASS` | 证据有效，所有配置阈值均满足 | 本次运行满足验收条件 |
| `FAIL` | 证据有效，至少一项阈值未满足 | 本次运行未满足性能要求 |
| `INVALID` | 样本不足或指标内部不一致 | 当前证据不足以支持性能结论 |
| 执行错误 | 输入加载、外部进程或数据处理等阶段失败 | 执行流程未完成，需要排查故障 |

证据有效性检查先于性能阈值检查。例如，样本不足不会直接归类为性能不达标。这种分层使自动化调用方能够区分验收结果与执行故障。

### 3.4 以 Run ID 关联输入与结果

每次运行使用独立目录保存测试输入快照、JTL、日志、指标和评估结果。Run ID 将这些产物关联起来，支持结果追溯、故障分析以及后续运行间对比。

目录创建和项目文件写入逻辑拒绝复用或覆盖已有目标。该策略防止工作流意外覆盖历史记录；当前未实现文件系统只读保护、内容完整性校验或防篡改存储。

### 3.5 控制外部进程的生命周期

Python 执行器负责构造 JMeter 命令，并区分命令不存在、执行超时、非零退出和输出文件缺失等情况。超时处理包含对子进程的清理，避免负载进程脱离编排流程持续运行。

进程行为具有平台差异。当前端到端验收环境为 Windows，多操作系统验证仍需补充。

### 3.6 用不同层次的测试验证不同风险

固定 JTL 数据集用于验证指标公式，模拟 JMeter 进程用于覆盖异常分支，端到端场景用于验证组件之间的集成。

自动化测试不依赖本地 JMeter 安装或外部网络。实际负载执行单独验收，使日常回归保持可重复，同时保留对真实执行链路的验证。

## 4. 验证结果与适用边界

M0 验收记录中的四类端到端场景得到以下结果：

| 场景 | 结果 | 验证重点 |
|---|---|---|
| 正常响应 | `PASS` | 满足阈值时的完整执行链路 |
| 慢响应 | `FAIL` | 响应时间阈值判定 |
| 错误响应 | `FAIL` | 成功率阈值判定 |
| 样本不足 | `INVALID` | 证据有效性判定 |

这些结果验证了受控 Demo API 场景下的执行与评估流程，不代表生产系统的容量结论或生产可用性验证。详细环境、指标口径和验收条件见 [M0 验证记录](m0-validation.md)。

当前范围为单机 JMeter、HTTP GET、CSV JTL、本地文件存储及单次运行的汇总指标。分布式负载、监控关联、自动报告和 AI 分析尚未纳入本阶段。

## 5. 后续改进

以下事项属于后续工作，不计入 M0 已交付能力：

| 方向 | 改进内容 | 工程收益 |
|---|---|---|
| 执行诊断 | 完善前置检查，在错误输出中统一携带 Run ID 和目录 | 缩短故障定位路径 |
| 产物管理 | 明确成功、失败和部分完成状态下的产物清单与保留策略 | 准确识别证据完整性 |
| 数据规模 | 评估大型 JTL 的内存占用，设计内存使用可控的处理方案 | 支持更大样本量 |
| 跨平台回归 | 增加多操作系统测试及 GitHub Actions CI | 验证进程管理与路径处理的兼容性 |
| 场景表达 | 扩展 HTTP 方法、请求头和请求体 | 支持更多被测接口 |
| 结果比较 | 明确配置、环境与指标口径的可比条件 | 支持运行间的性能回归分析 |

## 6. 对下一阶段的约束

M1 可在现有执行基础上引入 AI 测试规划器，将自然语言目标转换为 Test Spec。生成的规格仍需经过输入校验，并由现有执行器、指标计算和规则引擎处理。

引入自动规划时，还需明确执行授权、负载限制和人工审批机制；这些机制应作为后续设计内容，不能视为 M0 已完整实现的能力。

AI 规划与解释应引用实际输入、指标和规则结果，保留从结论到原始证据的追溯关系。
